## 1. Symbol Resolution (The "WHO" phase)

**Symbol Resolution** is the process of matching a **reference** (a request for a name) to a **definition** (the actual code/data).

- **The Problem:** In your code, main.o says: "I need to call a function called swap()". But main.o doesn't contain the code for swap(). It only contains a "placeholder" with the name "swap".
    
- **The Linker's Job:** The linker scans all the object files you provided (main.o, test1.o, libc.a, etc.). It looks for any file that says: "I have the definition for swap()".
    
- **The Result:** When the linker finds swap() inside test1.o, it "resolves" the symbol. It now knows that the swap requested by main is the one provided by test1.
    

**In short: Resolution is about finding the correct "owner" of a name.**

- Question it answers: **"Which function/variable are we talking about?"**

## 2. Symbol Relocation (The "WHERE" phase)

Once the linker knows who the symbol is, it needs to figure out where it is in the computer's memory.

- **The Problem:** When main.o was created, the compiler didn't know where the final program would be loaded in RAM. So, it used **Relative Addresses**.
    
    - Example: Instead of saying "Jump to address 0x4005", it says "Jump to the address of swap (currently unknown)."
        
- **The Linker's Job:** The linker merges all the .o files into one big executable. Now that they are all together, the linker can calculate the **Absolute Address**.
    
    - If the program starts at address 0x400000 and the swap() function happens to be located at the 1000th byte of the file, the linker calculates the real address: 0x400000 + 1000 = 0x4003E8.
        
- **The Result:** The linker goes back into the machine code of main.o and replaces the "placeholder" with the actual number 0x4003E8.
    

**In short: Relocation is about calculating and inserting the final memory address.**

- Question it answers: **"What is the exact physical address in RAM?**

## Definition vs. Declaration (The Secret of extern)

#### The Definition (The "Real" Object)

A definition creates the object and **allocates memory** for it.

- **Example:** int buf[2] = {1, 2};
    
- This tells the compiler: "Create a space in the .data section of memory, call it buf, and put the numbers 1 and 2 inside it."
    
- **There can only be ONE definition of a global symbol in the entire program.** (If you define it in two files, you get a "multiple definition" error).
    

#### The Declaration (The "Notice")

A declaration (using extern) does **NOT** allocate any memory. It is simply a notice to the compiler.

- **Example:** extern int buf[];
    
- This tells the compiler: "I am going to use a variable called buf. I am not creating it here. It already exists in some other file. Please just trust me and let me use the name."
    
- **You can have as many declarations as you want** across as many files as you like.

## Compiler Error and Run-Time-Error :

#### 1. Compile-Time Error (Syntax & Types)

- **When:** During the Preprocessing $\rightarrow$ Compiling $\rightarrow$ Assembling stage.
    
- **What:** The compiler is looking at **ONE file at a time**. It doesn't know about other files.
    
- **Examples:**
    
    - Missing a semicolon ;.
        
    - Using a variable that wasn't declared.
        
    - The "Implicit Declaration" error you saw earlier (because you didn't have a prototype).
        
- **Outcome:** No .o file is created.
    

#### 2. Link-Time Error (Symbols & Addresses)

- **When:** After all .o files are created, when the **Linker (ld)** tries to glue them together.
    
- **What:** The linker is looking at **ALL files together**. It is checking if the "Names" match.
    
- **Examples:**
    
    - **Undefined Reference:** You called swap(), but no file in the whole project defines it.
        
    - **Multiple Definition:** You defined void swap() { ... } in two different files (Rule 1 violation).
        
- **Outcome:** No executable file is created.
    

#### 3. Run-Time Error (Logic & Memory)

- **When:** The program is already compiled and linked; you are actually running the ./final file.
    
- **What:** The CPU is executing instructions and hits a physical memory problem.
    
- **Examples:**
    
    - **Segmentation Fault:** Trying to access memory you don't own.
        
    - **Logic Error:** The "junk value" you saw in GDB (1431666708). The program is "running," but the answer is wrong because the CPU looked in the wrong register.
        
- **Outcome:** The program crashes or produces wrong results.

## page 21 :
### 1. Relocatable Object Files (.o files) — "The Raw Ingredients"

These are the files created when you run gcc -c main.c.

- **What they are:** They contain machine code and data, but they are "incomplete."
    
- **Why "Relocatable"?** Because the addresses inside them are not fixed. They are just offsets (e.g., "the function swap is 10 bytes from the start of this file"). The Linker can move ("relocate") these blocks of code anywhere in the final memory layout.
    
- **The Rule:** Exactly one .c file produces exactly one .o file.
    
- **The "Error" shown on the slide:**  
    The slide shows a terminal error: Undefined symbols... "_x", referenced from: _main.  
    **This happens because** the user tried to turn a single .o file into an executable, but that file had an extern int x;. Since the Linker couldn't find any other .o file that provided the definition of x, it crashed.
    

### 2. Executable Object Files (a.out or final) — "The Finished Meal"

This is the final result after the Linker has done its job.

- **What they are:** The Linker has taken all the .o files, resolved all the symbols, and performed all the relocations.
    
- **Behavior:** These files are "Ready to Run." The OS can simply copy this file directly into RAM and tell the CPU to start executing at the Entry point.
    
- **Analogy:** This is the final "baked cake." You can't easily change one ingredient now without baking the whole thing again.
    

### 3. Shared Object Files (.so files) — "The Pre-made Sauce"

These are used for **Dynamic Linking**.

- **What they are:** A special kind of relocatable file that is **not** merged into the executable at compile time.
    
- **How they work:** Instead of copying the code of a library (like libc) into every single program on your computer (which would waste gigabytes of RAM), the code stays in one .so file on the disk.
    
- **Dynamic Linking:** When you run your program, the OS loads the .so file into memory **once**, and every running program shares that same piece of memory.
    
- **Analogy:** A shared sauce. Instead of every chef making their own ketchup from scratch, they all just use one giant bottle of store-bought ketchup.

### 1. The Three Lists (The "Memory" of the Linker)

The Linker keeps three lists on its clipboard:

1. **The Cart (E):The actual parts (object files) the Linker has decided to put in the final robot.
2. **The Shopping List (U):** A list of "missing parts" (symbols) that the robot needs but haven't been found yet.
3. **The Inventory (D): A list of all the "parts" (symbols) already inside the cart.
---

### 2. The Process (How the Shopper moves)

The Linker reads your gcc command from **Left to Right**.

#### Case A: The Shopper finds an Object File (.o)

When the Linker sees a .o file, it **must** take the whole thing. It's like buying a pre-assembled arm for the robot.

- **Action:** Put the .o file in the **Cart (E).
- **Update Inventory (D):"I now have all the symbols that were inside this file."
- **Update Shopping List (U): "This file also needs some other parts; I'll add those to my shopping list."

#### Case B: The Shopper finds an Archive/Library (.a)

An archive is like a **giant warehouse**. The shopper doesn't take the whole warehouse; they only take what they specifically need.

- **Action:** The Linker looks at the **Shopping List (U).
- **Search:** "Is there any specific object file inside this library that provides a symbol on my shopping list?"
- **Extract:** If yes, it takes **only that specific .o file** and puts it in the **Cart (E)
- **Loop:** Because that new .o file might need other parts, the Linker searches the library again and again until the shopping list is as empty as possible.

## page 31: ( dynamic linking )

### 1. The Problems with Static Libraries

The first two bullet points explain the "pain points" of static linking (where library code is copied directly into the final executable):

- **Relinking Requirement:** If you use a static library and the library developer releases a small bug fix, you cannot just replace the library file. You must **re-link** (and often re-compile) every single program that used that library to incorporate the fix.
    
- **Redundancy (Wasted Space):** Since every executable gets its own copy of the library code, if you have 10 different programs all using the same standard C library (libc), you have 10 copies of the same code taking up space on your hard drive and 10 copies taking up space in your RAM when those programs are running.
    

### 2. The Solution: Shared Libraries (.so files)

To solve these issues, Linux uses **Shared Objects** (files ending in .so). Instead of copying the library code into the executable, the linker just puts a "marker" or a reference in the executable saying, "I need a function called 'printf', and you can find it in libc.so."

### 3. How it Works at Runtime

Because the executable doesn't actually contain the library code, something must provide that code when the program runs:

- **ld-linux.so (The Dynamic Linker):** This is a special system program. When you start your app, ld-linux.so looks at the "markers" in your executable, finds the required .so files on the disk, and loads them into memory.
    
- **Memory Efficiency:** A key advantage is that the OS can load a shared library into memory **once**, and multiple different running processes can all share that same piece of physical RAM.
    

### 4. When does the linking happen?

The slide notes that dynamic linking can happen at two different times:

- **At Load Time:** This is the most common. The dynamic linker resolves all necessary symbols as soon as the program is started.
    
- **At Run Time (Explicitly):** A program can decide to load a library while it is already running. This is done using the **dlopen()** function. This is how "Plugins" or "Add-ons" work—the main program doesn't know about the plugin until it loads it from a file while executing.

## Dynamic :
### 3. Who does the work? (ld-linux.so)

In a computer, the program can't just "read a manual" on its own. It needs an assistant.

**ld-linux.so** is that assistant (the **Dynamic Linker**). When you double-click a program to run it, ld-linux.so wakes up, looks at the program's "references," finds the .so files (the manuals) on your hard drive, and plugs them into the program's memory so it can actually execute the code.

### 4. When does this happen? (The Timing)

The last bullet explains that this "plugging in" can happen at two different times:

1. **Load-time Linking:** The assistant (ld-linux.so) plugs in all the necessary libraries the very moment the program starts. If a library is missing, the program crashes immediately.
    
2. **Run-time Linking (dlopen()):** The program starts up normally, but later on—while it is already running—it decides it needs a specific tool. It calls dlopen() to say, "Hey, can you go find the 'Advanced Pastry' manual and plug it in for me right now?" (This is how **Plugins** and **Extensions** work).

##  Linking at runtime :
### 1. void *handle;

**What it is:** A generic pointer (called a "Void Pointer").  
**What it does:** It stores the **"Key"** to the library.

- **The Logic:** When you call dlopen(), the OS loads the .so file into RAM and says: "Okay, I've loaded the library. Here is a pointer to where it starts in memory."
    
- **Why void *?** Because the OS doesn't know what's inside your library; it just knows it's a block of memory. void * is used when we want a pointer to "something," but we don't care exactly what type it is yet.
    

---

### 2. void (*addvec)(int *, int *, int *, int);

**What it is:** A **Function Pointer**. (This is the hardest line to read in C).  
**What it does:** It is a **"Placeholder"** for the actual function.

Let's break down the weird syntax:

- void (*addvec) -> "I am creating a pointer named addvec that points to a function."
    
- (int *, int *, int *, int) -> "The function I am pointing to must take these 4 arguments (3 arrays and 1 number) and return nothing (void)."
    

**Why do we need this?**  
Normally, when you call a function, the compiler knows exactly where that function is. But here, the function is inside a .so file that hasn't been loaded yet! So, we create this pointer. Later, dlsym() will find the actual address of the function and "plug it into" this pointer.

---

### 3. char *error;

**What it is:** A string pointer.  
**What it does:** It stores **Error Messages**.

- **The Logic:** Runtime linking is risky. The library file might be missing, or the function name might be misspelled.
    
- **How it's used:** When something goes wrong, the function dlerror() generates a sentence (a string) explaining the problem (e.g., "File not found"). We store that sentence in the error variable so we can print it using printf.

## page 36:
###  The Secret Weapon: The GOT (Global Offset Table)

The library doesn't try to find the variable directly. Instead, it uses a "Directory" called the **GOT**.

- **What is the GOT?** It is a table located at the beginning of the **Data Segment**.
    
- **What does it do?** It stores the actual, absolute addresses of all global variables.
    
- **Who fills it?** The **Dynamic Linker** (ld-linux.so) fills the GOT with the correct addresses the moment the program starts.
**Key Takeaway:** PIC uses a **Relative Distance** to find a **Table (GOT)**, and the **Table** tells the program the **Absolute Address** of the data.

### 2. The Solution: The "Middlemen" (PLT and GOT)

To solve this, Linux doesn't call the function directly. Instead, it uses two "middlemen" tables: the **PLT** and the **GOT**.

#### **The PLT (Procedure Linkage Table)**

The PLT is a table of **small stubs** (tiny pieces of code).

- Instead of calling addvec() directly, your program calls the **PLT stub** for addvec.
    
- Think of the PLT as a **Switchboard Operator**. You don't call the person directly; you call the operator, and the operator connects you.
    

#### **The GOT (Global Offset Table)**

The GOT is the **Phonebook**. It stores the actual, absolute memory addresses of the functions.

- The PLT stub looks at the GOT to find the real address of the function.
    
- Once it finds the address in the GOT, it "jumps" to that address to execute the function.
    

**The flow looks like this:**
Main Program -> PLT Stub -> GOT Entry -> Actual Function in .so

**How it works the first time you call a function:**

1. You call the **PLT stub**.
    
2. The PLT sees that the **GOT entry** is empty (it doesn't have the address yet).
    
3. The PLT calls the **Dynamic Linker** (ld-linux.so).
    
4. The Dynamic Linker finds the real address of the function and **writes it into the GOT**.
    
5. The function is then executed.
    

**How it works every time AFTER the first call:**

1. You call the **PLT stub**.
    
2. The PLT looks at the **GOT** and sees the address is already there!
    
3. It jumps **directly** to the function. (It skips the dynamic linker entirely, making it very fast).

# Lecture 2 : ELF

## Exceptional Control Flow (ECF) :

To understand ECF, you have to compare it to the two other types of "flow" a CPU has:

### 1. Normal Flow (Sequential)

The CPU just goes in a straight line: Instruction 1 -> Instruction 2 -> Instruction 3.
### 2. Planned Flow (Programmed)

The CPU follows a "detour" that the programmer specifically wrote into the code using instructions like jmp (jump) or call (function call).

- Example: An if statement or a for loop. These are planned and expected.
    

### 3. Exceptional Flow (ECF)

This is a change in the path that is **not** part of the normal sequential line and was **not** a planned jump written by the programmer. It is "Exceptional" because it is a reaction to an event that happens outside the normal logic of the program.

---

### What actually causes ECF?

According to your slides (specifically page 5 and page 8), ECF is triggered by three main things:

**A. Hardware Interrupts (Asynchronous)**  
These are events external to the processor. The program has no idea they are coming.

- Examples: You click a mouse, a packet arrives from the internet, or a timer goes off.
    

**B. Traps (Synchronous & Intentional)**  
The program intentionally triggers an ECF to ask the Operating System (OS) for help.

- Example: A **System Call**. When a program wants to "Open a File," it cannot do it alone; it triggers a "Trap" to let the OS handle the hardware.
    

**C. Faults and Aborts (Synchronous & Unintentional)**  
The program does something wrong, and the CPU must stop it immediately to prevent the whole computer from crashing.

- Fault (Recoverable): A "Page Fault" (the data isn't in RAM yet, so the OS goes to the disk to get it).
    
- Abort (Non-recoverable): A "Segmentation Fault" (the program tried to access memory it doesn't own).

## page 6 :

### Page 6: How Exceptions Work?

This page explains the mechanism of moving from a **User Process** (your program) to the **OS** (the kernel).

#### 1. The Trigger: "An event causes a change in system state"

Everything starts with an **event**. This event is a signal that something has happened that the current instruction cannot handle alone.

- It could be internal (like dividing by zero).
    
- It could be external (like a keyboard press).  
    This "event" forces the CPU to stop what it is doing immediately.
    

#### 2. The Response: "OS defines exception handling procedures"


Think of an exception handler as an "Emergency Response Team." For every type of error or interrupt, the OS has a specific handler designed to fix that exact problem.

#### 3. The Timing: "Synchronous and asynchronous exceptions"

- **Synchronous:** The exception happens because of the instruction being executed (e.g., a divide-by-zero error). It happens at the same time as the instruction.
    
- **Asynchronous:** The exception happens independently of the instruction (e.g., a mouse click). It could happen at any time.
    

#### 4. Explaining the Diagram (The Flow)

If you look at the diagram on Page 6, follow the arrows:

1. **User Process** **`→`** **I_current**: The CPU is executing the "current instruction" (I_current).
    
2. **event** **`→`** **exception**: An event occurs. This triggers an "exception."
    
3. **exception** **`→`** **OS**: The CPU immediately stops the User Process and jumps across the boundary into the OS.
    
4. **exception processing**: The OS looks up the correct **Exception Handler** and runs it to deal with the event.

## page 7 :

#### Option 1: Return to the Current Instruction (I_current)

The OS sends the CPU back to the **exact same instruction** that was running when the exception happened.

- **Why?** This is used for **Faults**.
    
- **Example:** A "Page Fault." The CPU tried to read data, but the data wasn't in the RAM (it was on the disk). The OS handler goes to the disk, puts the data into RAM, and then tells the CPU: "Okay, try that same instruction again now that the data is actually there."
    

#### Option 2: Return to the Next Instruction (I_next)

The OS sends the CPU to the **instruction immediately following** the one that caused the exception.

- **Why?** This is used for **Traps** and **Interrupts**.
    
- **Example:** A System Call. You called a function to "print to screen." Once the OS finishes printing, there is no reason to run the "print" instruction again. The CPU simply moves on to the next line of your code.
    

#### Option 3: Abort the Interrupted Program

The OS decides that the error is too severe to fix and **kills the process**.

- **Why?** This is used for **Aborts**.
    
- **Example:** A "Segmentation Fault." Your program tried to write data into a restricted area of the kernel's memory. The OS sees this as a major security violation or a fatal crash and terminates the program entirely.

## page 8 : 
### 1. Interrupts (The "Doorbell")

- **Cause:** A signal from an I/O (Input/Output) device.
    
- **Async/Sync:** **Asynchronous**. An interrupt happens because a piece of hardware (like a keyboard, mouse, or disk drive) needs attention. The CPU doesn't know when this will happen.
    
- **Return Behavior:** **Always returns to the next instruction**.
    
    - Logic: Because the interrupt didn't "break" the current instruction—it just paused it—the CPU handles the hardware request and then simply continues with the program exactly where it left off (at the next instruction).
        

### 2. Traps (The "Request")

- **Cause:** Intentional exception.
    
- **Async/Sync:** **Synchronous**. The programmer explicitly wrote an instruction to trigger this exception.
    
- **Return Behavior:** **Always returns to the next instruction**.
    
    - Logic: The most common example is a **System Call**. The program says, "I want the OS to write this data to the disk." The "trap" is the signal to the OS. Once the OS finishes writing the data, the program has achieved its goal, so the CPU moves to the next line of code.
        

### 3. Faults (The "Hiccup")

- **Cause:** Potentially recoverable error.
    
- **Async/Sync:** **Synchronous**. The exception happened because the current instruction failed to execute.

The Theory of Asynchronous Interrupts

This slide defines what a hardware interrupt is and how the CPU physically perceives it.

#### 1. "Asynchronous" Nature

The most important word here is **asynchronous**. In computing, synchronous means "happening at the same time as something else." Asynchronous means "happening independently."  
An interrupt is asynchronous because it is **not** caused by the line of code the CPU is currently executing. If the CPU is running a loop to calculate math, and you press a key on your keyboard, the math code didn't cause the keyboard press. The event happened "outside" the program's timeline.

#### 2. The Physical Trigger: "The Interrupt Pin"

This is a key hardware detail. The CPU chip has physical electrical pins (small metal connectors). One of these is the **Interrupt Pin**.

- When a hardware device (like a network card or a keyboard) needs the CPU's attention, it sends an electrical signal (it sets the pin to "high" voltage).
    
- The CPU is designed to check the state of this pin periodically (usually at the end of every instruction cycle).
    

#### 3. Return Behavior: "Handler returns to next instruction"

Because the current instruction ( Icurr
) was perfectly fine and didn't cause the problem, there is no reason to repeat it. Once the OS handles the interrupt, the CPU simply picks up exactly where it left off—at the **next** instruction in the sequence.

#### 4. Real-World Examples

- **Ctrl-C:** You are telling the OS to kill a process. The keyboard sends a signal → Interrupt Pin goes high → OS stops your program

- **Network Packet:** Data arrives from the internet. The network card sends a signal → Interrupt Pin goes high → OS moves the data from the card to memory.

## page 11 :
#### 1. Traps (The "Intentional" Exception)

A trap is an exception that is triggered on purpose by the programmer.

- **How it works:** The programmer writes a specific instruction that tells the CPU: "Stop what you are doing and jump to the OS."
    
- **Primary Example: System Calls.** When a program needs to perform a privileged action (like reading a file from a hard drive or sending data over a network), it cannot do it directly for security reasons. It triggers a **Trap** to hand control over to the OS kernel, which performs the action safely.
    
- **Return Behavior:** It always returns to the **next** instruction. Once the OS has performed the requested task (e.g., opened the file), the program simply continues from where it left off.
    

#### 2. Faults (The "Fixable Error")

A fault is an unintentional error, but one that the OS might be able to fix "behind the scenes" without the program ever knowing something went wrong.

- **The Logic:** The CPU attempts an instruction → the instruction fails → the OS steps in, fixes the cause of the failure → the CPU tries the **same instruction again**.
    
- **Primary Example: Page Faults.** This is the most common fault. The program tries to access data in memory, but that data has been moved to the hard drive to save space. The CPU triggers a "Page Fault." The OS handler pauses the program, fetches the data from the disk back into the RAM, and then tells the CPU: "Try again; the data is here now."
    
- **Unrecoverable Faults:** Some faults cannot be fixed (like a "Protection Fault" where you try to write to a read-only memory area). In those cases, the Fault turns into an Abort.
    

#### 3. Aborts (The "Fatal Error")

An abort is an unintentional error that is so severe that it cannot be fixed.

- **The Logic:** The system detects a failure that makes it unsafe to continue execution. There is no "fixing" the state of the machine.
    
- **Examples:** **Hardware parity errors** (a bit in the RAM physically flipped from 0 to 1 due to interference) or a **Machine Check** (the CPU detected a hardware failure in its own circuits).
    
- **Return Behavior:** **Never returns**. The OS immediately kills the process (and sometimes the whole computer crashes/blue screens) to prevent the corrupted data from spreading or causing further damage.

Recall from slide 11 that a **Trap** is an intentional exception. A system call is a trap. The programmer writes code that intentionally triggers an exception to "knock on the door" of the OS.

The diagram shows the transition from a restricted environment to a privileged one:

The slide describes a situation where a "Memory page does not exist, but could be recovered from the disk."

### 1. The Definition: A Fatal Error

The slide begins by stating: **"An error with which the execution of the program cannot continue."**

In a computer, most errors can be handled. If a file is missing, the program can tell the user. If memory is missing (a Page Fault), the OS can fetch it. But an **Abort** happens when the CPU detects a condition where it can no longer guarantee that the results of its calculations are correct.

If the CPU cannot trust its own hardware, it is dangerous to keep running the program because the program might write corrupted data to the hard drive or perform an incorrect financial transaction.

---

### 2. The Cause: Hardware Corruption

The slide notes: **"In most cases the DRAM contains corrupted bits."**

This refers to a hardware-level failure, often called a **Machine Check Exception** or a **Parity Error**.

- **What happens physically:** Imagine a bit in your RAM (DRAM) physically flips from a 0 to a 1 due to electrical interference, heat, or a failing memory chip.
    
- **The Result:** If that bit was part of a critical instruction (e.g., changing a "Jump" to a "Delete"), the program's behavior becomes unpredictable.
    
- **Detection:** Modern CPUs have "Error Correction Code" (ECC) memory that can detect when a bit has flipped. When the hardware detects a corruption that it cannot automatically fix, it triggers an **Abort**.
    

---

### 3. The Workflow (The Diagram)

The diagram shows the "one-way street" of an abort. Unlike the other exceptions we studied, there is no arrow pointing back to the User Process.

#### Step (1): Fatal Hardware Error Occurs

The CPU is executing the current instruction ( **Icurr​** ). At this exact moment, the hardware detects a fatal error (like the DRAM corruption mentioned above).

#### Step (2): Control Passes to Handler

The CPU immediately stops execution. Because this is a synchronous exception, it happens exactly at **Icurr**. The CPU switches from **User Mode to Kernel Mode** and jumps to the OS's **Abort Handler**.

#### Step (3): Abort Handler Runs

The Abort Handler is a specialized piece of OS code. Its job is not to "fix" the program (because the hardware is corrupted, fixing the software is impossible). Instead, its job is **containment**. It must stop the corrupted process immediately so that the corruption doesn't spread to other programs or the OS kernel itself.

#### Step (4): Return to Abort Routine → "Abort"

The handler does not return to the user code. Instead, it calls a routine that:

1. Logs the error (so a system administrator can see that a RAM stick might be failing).
    
2. **Terminates the process** (kills the program).
    
3. Clears the memory used by that program.

### Slide 17: IA32 has an exception table

This slide explains how the hardware knows which "Emergency Response Team" (handler) to call when an exception occurs.

**1. The IDT (Interrupt Descriptor Table)**  
The IA32 processor doesn't "guess" what to do when an exception happens. It uses a hard-coded table in memory. Every exception is assigned a unique **Exception Number**. When the CPU detects an exception, it uses that number as an index into this table to find the memory address of the correct handler.

**2. The Numbering System**

- **Numbers 0–31:** These are reserved by the Intel/AMD processor designers for internal CPU events.
    
    - Example 0 (Divide Error): If you divide by zero, the hardware automatically triggers Exception 0 -> the OS Fault handler.
        
    - Example 14 (Page Fault): If a memory page is missing, the hardware triggers Exception 14 -> the OS Fault handler.
        
    - Example 18 (Machine Check): If the RAM is physically corrupted, the hardware triggers Exception 18 ->  the OS Abort handler.
        
- **Numbers 32–255:** These are "User Defined." The processor designers left these empty so that Operating System writers (like the creators of Linux or Windows) could define their own interrupts or traps.
    
- **The Special Case (128 / 0x80):** In Linux for IA32, the number **128 (hex 0x80)** is specifically reserved for **System Calls**. Whenever a program wants to ask the OS for something, it triggers Exception 128.
    

---

### Slide 18: Linux IA32 System Calls

This slide explains how Linux uses the "Trap" mechanism to provide services to user programs.

**1. The int n Instruction**  
In assembly language, int stands for "interrupt." The instruction int $0x80 literally tells the CPU: "Stop everything and trigger Exception Number 128 (0x80)." This is the "hammer" that forces the CPU to switch from User Mode to Kernel Mode.

**2. The System Call Table**  
Since int $0x80 is used for every single request (opening files, killing processes, reading keyboards), the OS needs a way to know which specific service the program wants.  
The OS maintains a **System Call Table**. The program must put a "Service Number" into a CPU register before calling int $0x80.

- **Number 1:** exit (Terminate the process)
    
- **Number 2:** fork (Create a new process)
    
- **Number 4:** write (Send data to a file or screen)
    
- **Number 5:** open (Access a file)

### Slide 19: How a system call is made?

This slide is the "technical map" showing how a C function call turns into machine instructions.

**1. The Gap: High-Level** -> **Low-Level**  
In C, you write write(1, "Hello", 13);. But the CPU cannot execute C code; it only understands registers and opcodes.

**2. Register-Based Parameter Passing**  
Passing data via the "stack" (memory) is slow. To make system calls fast, Linux uses **CPU Registers** as a "mailbox" to send information to the kernel.

- **%eax (The Command):** This register must hold the **System Call Number**. (e.g., 4 for write).
    
- **%ebx, %ecx, %edx, etc. (The Arguments):** These registers hold the details of the request.
    
    - For write(1, "Hello", 13):
        
        - %ebx = 1 (The file descriptor for standard output/screen).
            
        - %ecx = The memory address of the string "Hello".
            
        - %edx = 13 (The length of the string).
            

**3. The Assembly Sequence**  
Look at the provided code:

1. movl $4, %eax -> "I want service #4 (write)."
    
2. movl $1, %ebx ->  "Write it to the screen (1)."
    
3. movl $string, %ecx -> "Here is the text to write."
    
4. movl $len, %edx ->  "The text is this many bytes long."
    
5. int $0x80 -> **TRAP!** The CPU jumps to the OS kernel.

### Slide 20: System call wrapper

Writing assembly code (movl, int $0x80) for every single print statement would be a nightmare for programmers. This is why we use **Wrappers**.

**1. What is a Wrapper?**  
A wrapper is a high-level library function (usually part of the **C Standard Library / libc**) that hides the ugly assembly code.

**2. The Layer Cake of Execution**  
When you call printf("Hello"), the following chain happens:

1. **printf() (The High-Level Wrapper):** This is a very "smart" function. It handles formatting (like converting numbers to text). Once it has the final string, it calls the next layer.
    
2. **write() (The System Call Wrapper):** This is a simpler function. It doesn't do formatting; it just takes the string and prepares the CPU registers (%eax, %ebx, etc.) as shown on Slide 19.
    
3. **int $0x80 (The Hardware Trap):** The wrapper executes the assembly instruction to jump into the kernel.
    
4. **sys_write (The Actual Kernel Routine):** The OS kernel receives the request, checks permissions, and physically tells the hardware to put pixels on the screen.
    

**The Benefit:** The programmer only has to care about printf(). They don't need to know that the CPU is using register %eax or triggering exception 0x80 behind the scenes.


## High-level and Low-level :
### 1. Low-Level Languages

Low-level languages are "close to the metal." They provide little to no **abstraction**, meaning they don't hide how the computer actually works. If you want to move a piece of data, you have to tell the CPU exactly which register to use.

There are two types of low-level languages:

- **Machine Code (Binary):** This is the only language a CPU actually understands. It consists entirely of 0s and 1s.
    
    - Example: 10110000 01100001 (This might mean "move the value 97 into a register").
        
- **Assembly Language:** Since humans cannot read binary, Assembly was created. It uses "mnemonics" (short words) to represent binary instructions.
    
    - Example: mov eax, 1 (This is the human-readable version of the binary above).
        

#### Characteristics of Low-Level Languages:

- **Hardware Dependent:** Assembly written for an **IA32** (Intel) processor will not work on an **ARM** (Apple M1 or Android) processor.
    
- **Total Control:** You control exactly how memory is used and which registers are touched.
    
- **High Efficiency:** Because there is no "middleman," the code is incredibly fast and uses very little memory.
    
- **Difficult to Write:** Simple tasks (like printing "Hello") require many lines of code.
    

---

### 2. High-Level Languages

High-level languages are designed to be readable by humans. They use **abstraction** to hide the complex hardware details. You don't need to know how the CPU registers work to write a program in Python or Java.

- Examples: Python, Java, JavaScript, C#, and (to a large extent) C++.
    

#### Characteristics of High-Level Languages:

- **Hardware Independent (Portable):** You can write a Python program on a Mac and run it on a Linux server without changing the code. The "interpreter" or "compiler" handles the hardware differences.
    
- **Abstraction:** You use concepts like variables, loops, and objects instead of memory addresses and registers.
    
- **Easy to Write:** You can do in one line of Python what might take 20 lines of Assembly.
    
- **Less Efficient:** Because the code must be translated into machine code by a compiler or interpreter, it is usually slower and uses more RAM.
    

---

### 3. The "Middle Ground": The C Language

In your course, you are using **C**. C is often called a **"Mid-Level"** or **"Portable Assembly"** language.

Why? Because C gives you the best of both worlds:

1. **High-Level Side:** It has a readable syntax, loops, and functions.
    
2. **Low-Level Side:** It allows you to manipulate memory directly using **Pointers** and allows you to call **System Calls** (like the write function you tried).
    

**This is why C is used to write Operating Systems (like Linux).** It is fast enough to be efficient, but readable enough for humans to maintain.

## page 22 :
### 1. The OS as a Low-Level Hardware Layer

**"Operating systems (OS) include a layer of low level system software that interacts with the hardware."**

At the bottom of your computer is the **Hardware** (the CPU, the RAM sticks, the hard drive, the network card). Hardware is "dumb"—it only understands electrical signals and binary.

If every program you wrote had to personally tell the hard drive's motor how to spin and the read-head where to move, programming would be nearly impossible. The OS provides a **Layer of Abstraction**. Instead of talking to the hardware, your program talks to the OS, and the OS talks to the hardware.

The "core" of this layer is called the **Kernel**. The Kernel is the part of the OS that is always in memory and has **privileged access** to the hardware.

### 2. Resource Management

**"For example, OS manages the hard disk, the memory, and the interaction with the CPU."**

The OS acts as a "Manager" or "Referee" for three critical resources:

- **Memory (RAM):** The OS decides which program gets which part of the RAM. It ensures that Program A cannot read or write into the memory of Program B (which is why you get a "Segmentation Fault" if you try).
    
- **Hard Disk:** The OS manages the "File System." It keeps track of where a file actually starts and ends on the physical disk so you can just refer to it by a name like document.txt.
    
- **CPU:** The OS manages **Scheduling**. Since you might have 50 programs open but only 4 or 8 CPU cores, the OS decides who gets to use the CPU right now and for how many milliseconds.
    

### 3. Program Lifecycle and Services

**"Operating systems are responsible for loading programs into memory and providing all the necessary services for them to run."**

A program on your hard drive is just a dead file (an "executable"). To make it "come alive," the OS performs several steps:

1. **Loading:** The OS reads the executable file from the disk and copies the code into a fresh area of RAM.
    
2. **Setup:** The OS sets up the **Stack** (for local variables) and the **Heap** (for dynamic memory), as you will see in later slides.
    
3. **Execution:** The OS tells the CPU to start executing the first instruction of the program.
    

Once the program is running, it will inevitably need "services"—like printing text to the screen or getting the current time. The OS provides these services as a utility.

### 4. The Gateway: System Calls

**"User programs interact with the operating system through the system call functions."**

This is the most important point for your course. Because the OS has privileged access to the hardware, it cannot let a User Program just "jump" into the Kernel whenever it wants. That would be a massive security hole (a virus could simply tell the OS to "delete everything on the disk").

Therefore, the OS creates a **Secure Gateway**.

- The User Program cannot touch the hardware.
    
- The User Program cannot touch the Kernel's memory.
    
- The **ONLY** way a program can ask the OS to do something is by using a **System Call**.
    

As you learned in slides 13–20, a system call is essentially a "request form." The program fills out the request in registers, triggers a **Trap** (int $0x80), and the OS decides if the request is legal before performing it.

### Slide 23: How does OS manage program executions?

This slide introduces one of the most fundamental concepts in computer science: the difference between a **Program** and a **Process**.

#### 1. Program vs. Process

To understand this, you have to distinguish between "static" and "dynamic."

- **A Program** is a **static** entity. It is just a file sitting on your hard drive (like chrome.exe or main.out). It does nothing; it is just a collection of bytes.
    
- **A Process** is a **dynamic** entity. It is a "unit of program execution." When you double-click a program, the OS "activates" it. It loads the code into RAM, assigns it resources, and gives it a life. That "living" version of the program is the **Process**.
    

#### 2. The Process as a Managed Entity

The OS doesn't just "start" a process and forget about it. It must maintain a "folder" of information for every process it runs. This is what the slide means by **"maintained by OS with a set of data structures."** (In professional terms, this "folder" is called the **Process Control Block** or **PCB**).

The OS needs to track these specific things for every single process:

- **Program Code:** The actual machine instructions the CPU needs to execute.
    
- **Open Files:** If your program opened three text files, the OS must keep a list of those files so it knows where to read/write data.
    
- **The Stack:** This is a region of memory used for temporary data, such as function arguments, return addresses, and local variables.
    
- **The Heap:** This is a region of memory used for "dynamic" data—things you create while the program is running (for example, using malloc in C).
    

**Key Takeaway:** A process is not just the code; it is the **Code + the Memory (Stack/Heap) + the OS tracking data**.

### Slide 24: OS uses events to provide concurrency

Now that we know what a process is, this slide explains how the OS runs many processes at the same time on a single CPU. This is called **Concurrency**.

#### 1. Interleaved Execution

If you have one CPU core but you are running Spotify, Chrome, and VS Code at the same time, it feels like they are all running simultaneously. However, on a single core, they actually aren't.

The OS uses **Interleaving**. It lets Process A run for a tiny fraction of a second (e.g., 10 milliseconds), then it stops Process A and lets Process B run for 10 milliseconds, and then Process C. Because this happens thousands of times per second, it creates the **illusion** of concurrency.

#### 2. The Role of the Kernel

The only way the OS can force a process to stop so that another can start is by using **Kernel Code**.

- **The Kernel** is the specialized part of the OS that lives in its own protected region of memory.
    
- It has **full access** to the entire machine's memory and hardware.
    
- The Kernel acts as the "Director." It uses a timer (a hardware interrupt) to "wake up" and decide: "Process A has had enough time; I am now going to switch the CPU to Process B."
    

#### 3. Explaining the Diagram

The diagram visually represents this "switching" behavior over time.

- **The Y-Axis (Time):** Time moves downward.
    
- **Horizontal Lines:** These represent the CPU executing a process.
    
- **The Gaps:** Notice how the line for Process A stops and then starts again later. During that gap, the CPU was busy executing Process B or C.
    
- **"Same or multiple cores":**
    
    - On a **single-core CPU**, the lines must be staggered (one after another) because only one thing can happen at a time.
        
    - On a **multi-core CPU**, the OS can run Process A on Core 1 and Process B on Core 2 at the exact same time. This is called **Parallelism**.

### Slide 25: The Concept of Context

This slide asks: How can the OS stop Process A, run Process B, and then come back to Process A exactly where it left off?

The answer is the **Context**. The context is a "snapshot" of everything the CPU needs to restart a process. If the OS doesn't save the context, the program will crash or produce wrong results when it resumes.

**What exactly is in a "Context"?**

1. **Registers:** These are the CPU's internal "scratchpads." If Process A was halfway through a math problem (e.g., it had the number 42 stored in register %eax), that value must be saved.
    
2. **The PC (Program Counter):** This is the "bookmark." It is the memory address of the very next instruction the CPU was supposed to execute.
    
3. **User's Stack:** This contains the local variables and the "return addresses" (where the program should go after a function finishes).
    
4. **The Page Table:** This is the most complex part. It is a map that tells the CPU: "Virtual Address X in this program actually lives at Physical RAM Address Y." Every process has its own unique map.
    
5. **Process/File Tables:** A list of which files the program has open and what its "PID" (Process ID) is.
    

**Analogy:** Imagine you are reading a book. Your "context" is your bookmark (PC), the notes you've scribbled in the margins (Registers), and the page you are on. If someone takes the book away, you can only resume if you have that bookmark and your notes.

---

### Slide 26: The Mechanism (The Context Switch)

This slide explains the actual **action** of swapping processes. This is called a **Context Switch**.

**The three-step process:**

1. **Save:** The OS takes the current values in the CPU registers and the PC and writes them into a data structure in memory (the Process Control Block).
    
2. **Restore:** The OS looks up the "saved snapshot" of the next process and loads those values back into the CPU registers and the PC.
    
3. **Pass Control:** The CPU now has the new program's "bookmark" in the PC. It simply begins executing.
    

**Explaining the Diagram:**  
Look at the flow: **User Code** **→** **Kernel Code  →** **User Code.**

- A context switch **cannot** happen in "User Code." A user program cannot save its own context or change the CPU's page tables (that would be a security risk).
    
- Therefore, an event (like a timer interrupt) must first trigger an ECF to jump into the **Kernel**.
    
- The **Kernel** (the privileged OS code) performs the save/restore operations.
    
- Once the switch is complete, the Kernel jumps back out to the **User Code** of the new process.

### 1. The Starting State: Process A is Running

At the very top, the CPU is executing **Process A** in **User code**. The CPU's registers and Program Counter (PC) are currently loaded with Process A's data.

### 2. The Trigger: The read System Call

Process A reaches a line of code that says read(file, buffer, length).

- **The Action:** As we learned in previous slides, read is a **System Call (a Trap)**.
    
- **The Transition:** The CPU immediately stops executing User code and jumps into **Kernel code**.
    
- **The Problem:** Reading from a disk is incredibly slow. If the CPU waited for the disk to find the data, it would waste millions of clock cycles doing nothing. This is called "blocking."
    

### 3. The First Context Switch (Process A → Process B)

Because Process A is now "blocked" (waiting for the disk), the OS decides to use the CPU for something else so that no time is wasted.

- **Saving A:** The OS saves the **Context** of Process A (the current values of its registers, its current PC, and its stack pointer) into memory.
    
- **Loading B:** The OS loads the saved **Context** of **Process B** into the CPU's registers and PC.
    
- **Switching:** The CPU jumps from Kernel code into **Process B's User code**.
    
- **Observation:** On the diagram, you see the line move horizontally from the "Process A" column to the "Process B" column. This movement is the **Context Switch**.
    

### 4. The "Gap": Process B Executes

While the disk is still working in the background to find the data for Process A, the CPU is now fully occupied running **Process B**. Process B has no idea that Process A even exists; it just thinks it's its turn to run.

### 5. The Wake-Up: The Disk Interrupt

Suddenly, the hard drive finishes reading the data. It sends an electrical signal to the CPU's **Interrupt Pin** (which we studied on slide 9).

- **The Action:** This is an **Asynchronous Interrupt**.
    
- **The Transition:** The CPU immediately pauses Process B and jumps back into **Kernel code** to handle the interrupt.
    

### 6. The Second Context Switch (Process B → Process A)

The OS's Interrupt Handler realizes: "The data that Process A was waiting for is finally here!"

- **Saving B:** The OS saves the current context of Process B (so it can return to it later).
    
- **Restoring A:** The OS retrieves the saved context of Process A that was stored way back in Step 3. It loads Process A's registers and its "bookmark" (the PC).
    
- **Resuming:** The CPU jumps back into **Process A's User code**.
    

### 7. Completion: Return from read

Process A resumes exactly where it left off. To the programmer, it looks like the read() function just finished and returned the data. Process A has no idea it was "paused" and that Process B was running in the meantime.

---

### Summary of the Technical Logic

If you are asked to explain this diagram on an exam, use these key points:

1. **Efficiency:** The goal is to prevent the CPU from idling while waiting for slow I/O (the disk).
    
2. **Privilege:** The switch always happens in **Kernel code**, never in User code.
    
3. **The "Snapshot":** The transition between the columns (A → B and B → A) is only possible because the OS saves the **Context** (Registers, PC, Stack).
    
4. **Event-Driven:** The switch back to Process A is triggered by a **Hardware Interrupt** from the disk.

## page 27 :
### Slide 27: Private Address Space (Virtual Memory)

This slide explains how the OS prevents processes from stealing or crashing each other's data.

**The Big Secret: Virtual Memory**  
In a modern computer, a program never knows where it "actually" is in the physical RAM sticks. Instead, the OS gives every process a **Private Address Space**.

Every process thinks it has a huge, empty block of memory all to itself, starting from address 0. This is called a **Virtual Address**. The hardware (the MMU) and the OS translate these virtual addresses into real physical addresses on the fly.

**The Memory Map (The Diagram):**  
If you look at the memory layout from top to bottom:

1. **Kernel Virtual Memory:** The top part of the address space is reserved for the OS. It is "invisible" to the user. If a program tries to touch this area, the CPU triggers a **Segmentation Fault (Abort)**.
    
2. **User Stack:** This is at the top of the user area. It grows **downward**. It stores local variables and function calls.
    
3. **Memory-Mapped Region:** This is where shared libraries (like the C library libc) are loaded so multiple programs can use them without wasting RAM.
    
4. **Run-time Heap:** This grows **upward**. This is the memory you get when you call malloc() in C.
    
5. **Read-Write/Read-Only Segments:** The bottom of the memory.
    
    - **.text**: The actual machine code instructions (Read-only).
        
    - **.data**: Your global variables (Read-write).
        

**Why is this important?**  
Because Process A and Process B both have their own private maps. Process A might have data at virtual address 0x100, and Process B might also have data at virtual address 0x100. But because their **Page Tables** are different, those two identical virtual addresses point to two **different physical locations** in the RAM.

**This is the ultimate security wall: Process A physically cannot "see" Process B's memory because it doesn't have a map to get there.**

## fork :
### Slide 28: How a program creates a process?

This slide introduces the mechanism for process creation in Unix-like systems (Linux).

#### 1. The fork() System Call

In most languages, if you want a new process, you might think you "start" a new program. But in Linux, you use fork().  
**fork() does not start a new program; it clones the current one.**

When a process calls fork(), the OS creates a brand new process (the **Child**) that is an exact duplicate of the original process (the **Parent**). This includes a copy of the code, the variables, the stack, and the current state of the CPU.

#### 2. The "Dual Return" (The most important part)

The most confusing thing about fork() is that it is **called once, but it returns twice.**

- It returns once in the **Parent** process.
    
- It returns once in the **Child** process.
    

Because the Child is a perfect clone, it starts executing from the exact same line where the fork() call happened. To prevent the Parent and Child from doing the exact same thing forever, fork() returns different values to each:

- **To the Child:** fork() returns **0**.
    
- **To the Parent:** fork() returns the **PID (Process ID)** of the new child (a number greater than 0).
    

#### 3. Explaining the Code Example

codeC

```
pid_t pid = fork(); 
if (pid == 0) { 
    printf("hello from child\n"); 
} else { 
    printf("hello from parent\n"); 
}
```

- When fork() is called, the process splits.
    
- The **Child** looks at its pid variable, sees it is 0, and enters the if block.
    
- The **Parent** looks at its pid variable, sees it is a positive number (the child's ID), and enters the else block.

### Slide 29: Creating a process: fork (The Details)

This slide explains the "physics" of what happens to the memory and resources during a fork().

#### 1. Exact Copy vs. Separate Address Space

The slide states: **"Parent process creates the child, with an exact copy of its code"** but **"Parents and children have duplicate but separate address spaces."**

This is a critical distinction. While the Child starts as a copy, it is not "linked" to the Parent. They are now two separate entities in the RAM. If the Child changes a variable, the Parent’s variable **does not change**.

#### 2. Explaining the fork1() Example

This code is designed to prove that the memory is separate:

codeC

```
int x = 1;
pid_t pid = fork();
if (pid == 0) {
    printf("Child has x = %d\n", ++x); // Child increments x to 2
} else {
    printf("Parent has x = %d\n", --x); // Parent decrements x to 0
}
printf("Process %d, x = %d\n", getpid(), x);
```

**What happens here:**

1. Before the fork, there is one variable x with the value 1.
    
2. After fork(), there are now **two separate variables** named x in two different memory locations.
    
3. The Child increments its x to **2**.
    
4. The Parent decrements its x to **0**.
    
5. The final printf will show that the Child's x is 2 and the Parent's x is 0.
    

This proves that they do **not** share memory.

#### 3. Shared File Descriptors

While memory is separated, **Open Files** are shared.  
**"Child, on creation, shares open file descriptors such as stdout with parent."**

This is why both the Parent and the Child can print to the same terminal screen. They both have a "pointer" to the same output stream (stdout). If the Parent opens a file and then forks, the Child can read or write to that same file without having to open it again.

### Slide 31: Exiting a Process

This slide explains how a process "dies" and how to perform cleanup before it disappears.

**1. exit(status)**  
A process doesn't just stop; it must tell the OS how it ended. exit(0) tells the OS the program finished successfully. Any other number (like exit(1)) usually indicates an error.

**2. atexit() (The Cleanup Register)**  
Sometimes a program needs to do something before it dies (e.g., delete a temporary file or close a database connection). atexit() allows you to register a function to be called **automatically** just before the process terminates.

**3. Example fork6() Analysis:**

- atexit(cleanup) is called. This registers the cleanup function.
    
- fork() is called → the process splits into two.
    
- **Crucial Point:** Because the Child is a clone of the Parent, it **also inherits the registered cleanup function**.
    
- Both processes call exit(0).
    
- **Result:** The cleanup function runs **twice** (once for the parent, once for the child). You will see "cleaning up" printed twice.

### The Answer: It copies ALL the code, but starts AFTER the fork().

Imagine a video game. You have played for 2 hours and reached **Level 10**. You save your game.

Now, imagine you "clone" your save file. You now have two identical save files. When you open the second save file, **do you have to start the game from Level 1 again?**

**No.** You start exactly at **Level 10**, because that's where the "save" was made.

**That is exactly how fork() works:**

1. **The Copy:** The Child gets a perfect copy of the **entire** program (the "save file"). It has all the code from the beginning of main() to the end.
    
2. **The Execution:** The Child does **not** start from the first line of main(). It starts at the **Program Counter (PC)** location where the fork() happened.
    
3. **The Result:** The Child begins its life at the exact moment the fork() call returns.

### Why does this happen? (Connecting to Slide 31)

1. **The Registration:** The Parent calls atexit(cleanup). The OS marks a "note" in the Parent's process data: "When this process dies, run the cleanup function."
    
2. **The Clone:** When fork() happens, the Child is a **perfect clone**. It doesn't just copy the code; it copies the **"notes"** too.
    
3. **The Inheritance:** The Child now also has the "note" saying: "When I die, run the cleanup function."
    
4. **The Double Execution:**
    
    - The Child calls exit(0) → OS sees the note → **Cleanup runs once.**
        
    - The Parent calls exit(0) → OS sees the note → **Cleanup runs again.**
        

**Final Proof:**  
If the child started from the beginning of main(), it would have called atexit(cleanup) a second time. But because it starts **after** the fork(), it simply inherits the registration that was already there.

### Question 1: How does the Child do the cleanup if atexit was called before the fork?

To understand this, you have to remember the most important rule of fork() from Slide 28 and 29: **The Child is a perfect clone of the Parent.**

#### 1. What atexit actually does

When you call atexit(cleanup), the program does not run the cleanup function immediately. Instead, it registers the function.

Inside the process's memory, the C library maintains a **"Registration List"** (a small array of function pointers). Calling atexit simply adds the address of the cleanup function to that list. It's like writing a note to yourself: "Remember to take out the trash before you leave the house."

#### 2. The "Cloning" of the List

When fork() is called, the OS creates a duplicate of the **entire address space**. This means the Child gets:

- A copy of the code.
    
- A copy of the variables.
    
- **A copy of the Registration List.**
    

Because the Parent had already registered cleanup before the fork, the Child is born with that same registration already in its memory. The Child doesn't need to call atexit itself because it **inherited** the registration from the Parent.

#### 3. The Trigger

Now, both the Parent and the Child have the "note" in their memory.

- When the Child calls exit(0), the C runtime library checks the Registration List. It sees cleanup on the list  →  it runs cleanup().
    
- When the Parent calls exit(0), it also checks the list. It sees cleanup on the list  →  it runs cleanup() again.
    

**In short:** The Child can perform the cleanup because atexit modifies the process's internal state, and fork() clones that state perfectly.

### The Short Answer:

Only the process that actually calls atexit() will run the cleanup. The other process will **not** run it.

---

### The Detailed Explanation (The Timeline)

Let's look at the timeline of events to see why this happens.

#### 1. The Fork (The Split)

When fork() is called, the OS creates a perfect clone. At this exact moment, the "Registration List" (the list of functions to run at exit) is **empty** for both the Parent and the Child.

#### 2. The atexit Call (The Registration)

Now, the code moves to the atexit(cleanup) line. Because the processes are now **separate**, they each have their own independent memory.

- **If only the Parent calls atexit:** Only the Parent's registration list is updated. The Child's list remains empty.
    
- **If only the Child calls atexit:** Only the Child's registration list is updated. The Parent's list remains empty.
    
- **If both call it:** Both will run it (but they are doing it independently).
    

#### 3. The Exit

- When the process that **didn't** call atexit dies, the OS looks at its registration list, sees it is empty, and simply closes the process. **No cleanup runs.**
    
- When the process that **did** call atexit dies, the OS sees the cleanup function on the list and runs it.

### Slide 32: Sharing a File Example

This slide explains the one thing that is **NOT** separated during a fork(): **Open File Descriptors**.

**1. The Concept**  
As we saw in Slide 29, the Parent and Child have separate memory. If the Parent changes a variable, the Child doesn't see it. **However**, if the Parent opens a file before forking, the Child shares the **same open file pointer**.

**2. The Workflow in the Code:**

1. fopen("new_file.txt", "a+"): The Parent opens a file in "append" mode.

3. **Writing:**

4. **The Result:** Both messages appear in the same file.

- If the Child writes 15 bytes, the cursor moves forward 15 bytes.

- **This prevents the processes from overwriting each other's data.** They work together to append to the same file.

### Slide 33: Zombies: Half Alive, Half Dead

This slide introduces a very strange concept in Linux: the **Zombie Process** (also called a **defunct** process).

#### 1. What is a Zombie?

In a normal world, when someone dies, they are gone. But in Linux, when a child process terminates (dies), it doesn't disappear completely. It enters a "Zombie" state.

**Why?** Because the Parent might want to know how the child died. Did it finish successfully? Did it crash with an error? To store this "exit status," the OS keeps a tiny piece of the child's information (its PID and exit code) in the system process table.

**A Zombie is a process that is dead, but still has an entry in the system table.**

#### 2. What is "Reaping"?

"Reaping" is the act of the Parent process acknowledging the child's death. When the Parent calls a function like wait(), it reads the child's exit status. At that exact moment, the OS says, "Okay, the parent knows now," and it finally deletes the zombie from the system table.

#### 3. The Danger of Zombies

If a parent is poorly written and never "reaps" its children, the system table fills up with zombies. Since the table has a limited size, too many zombies can prevent the computer from starting any new processes.

#### 4. What if the Parent dies first?

If the Parent dies without reaping the child, the child becomes an "orphan." Linux handles this by having a special process called **init** (PID 1), which is the "grandfather" of all processes. The init process automatically adopts all orphans and reaps them immediately so they don't become permanent zombies.

### Slide 36: wait exit status

In slide 34, we learned that wait() stops the parent. But as a programmer, you don't just want to know that a child died; you want to know why it died.

#### 1. The child_status Integer

When you call wait(&child_status), the OS doesn't just return a number. It writes a complex "bit-field" (a packed integer) into that variable. This integer contains multiple pieces of information:

- Did the child exit normally?
    
- Did it crash (e.g., Segmentation Fault)?
    
- What was the exit code (the number in exit(n))?
    

Because this integer is packed with binary data, you cannot just print it. You must use **Macros** to "unpack" the data.

#### 2. The Macros

- **WIFEXITED(status)**: (Wait If Exited). This returns **TRUE** if the child terminated normally (i.e., it called exit() or returned from main). It returns **FALSE** if the child was killed by a signal (like a crash).
    
- **WEXITSTATUS(status)**: This extracts the **actual exit code**. If the child called exit(100), this macro will return 100.
    

#### 3. The fork10() Example

In the code, the parent forks  N  children. Then it enters a second loop to reap them.

- It calls wait(&child_status).
    
- It uses WIFEXITED to check if the death was "clean."
    
- If clean, it uses WEXITSTATUS to print the specific exit code the child sent back.

### Part 1: The Setup (Variables)

codeC

```
pid_t pid[N];
int i;
int child_status;
```

- **pid[N]**: This is an array of Process IDs. The parent needs this list so it can remember exactly which children it created.
    
- **child_status**: This is a "placeholder" integer. When a child dies, the OS will write the child's exit information into this variable.
    

---

### Part 2: The Creation Phase (The First Loop)

codeC

```
for (i = 0; i < N; i++)
    if ((pid[i] = fork()) == 0)
        exit(100 + i); /* Child */
```

This loop creates  N  children. Let's look at the logic inside:

1. **pid[i] = fork()**: The parent calls fork(). The resulting Process ID is saved into the array pid.
    
2. **if (... == 0)**: This is the "split."
    
    - **For the Parent:** The if is **False**. The parent ignores the exit line and goes back to the top of the loop to create the next child.
        
    - **For the Child:** The if is **True**. The child enters the block.
        
3. **exit(100 + i)**: This is the most important part. The child doesn't just die; it dies with a **unique status code**.
    
    - If it's the 1st child (  i=0 ), it exits with **100**.

### 1. The "Death" is not immediate (exit)

When a child process calls exit(100 + i), it doesn't just vanish from the computer's memory instantly.

The OS allows the child to stop executing code, but it **keeps the child's "ghost"** in the system's Process Table. This "ghost" is called a **Zombie Process**.

**Why does the OS do this?**  
Because the parent might want to know: "Did my child finish the job? Did it crash? What was the result?" The OS stores the exit status (the 100 + i value) in that Zombie entry so the parent can read it whenever it is ready.

---

### 2. The "Cleaning" process (wait)

This is where wait() comes in. Even though the children have already called exit(), they are still taking up a tiny bit of space in the OS Process Table as Zombies.

When the parent calls wait():

1. **The OS checks:** "Is any of this parent's children dead?"
    
2. **The OS delivers:** "Yes, Child #5 is dead. Here is the exit status he left behind: 105."
    
3. **The OS deletes:** Now that the parent has received the message, the OS finally deletes the Zombie from the Process Table.
    

**This act of deleting the zombie is called "Reaping."**

---

### 3. What happens if you DON'T call wait()?

If the children all call exit() but the parent **never** calls wait(), you get a **Zombie Apocalypse**.

- The children are dead, but their entries remain in the system table.
    
- If your program creates thousands of children and never calls wait(), the Process Table will fill up.
    
- Once the table is full, your computer **cannot start any new processes**. You won't be able to open a new terminal, start a browser, or even run ls. The system will freeze or crash.

### The Problem with wait()

As you saw in your last experiment, wait() is a "blind" function. It says: "I don't care which child dies; just tell me when **any** of them are finished."

Imagine you have 3 children:

- **Child A** is doing a quick task (1 second).
    
- **Child B** is doing a medium task (5 seconds).
    
- **Child C** is doing a huge task (1 hour).
    

If you use wait(), you can only reap them in the order they die. You can't say, "I want to make sure Child C (the big task) is finished before I move on," because wait() might return Child A first, then Child B, and you'd still be waiting for C.

**waitpid() is the solution. It allows the parent to be specific.**

---

### 1. The Function Signature

pid_t waitpid(pid_t pid, int *status_ptr, int options);

Think of this function as a **Request Form** you send to the OS. You fill out three fields:

1. **pid (The Target):** Who am I waiting for?
    
    - If you put a **specific PID** (e.g., 897), the parent says: "I only care about Child 897. Ignore everyone else."
        
    - If you put **-1**, the parent says: "I don't care who it is, just give me whoever dies first." (This makes waitpid behave exactly like wait).
        
2. **status_ptr (The Note):** Where should the OS put the exit status?
    
    - Just like wait(), this is where the WIFEXITED and WEXITSTATUS info goes.
        
3. **options (The "How"):** How should I wait?
    
    - This is the most powerful part of the function.
        

---

### 2. The "Options" (The Superpowers of waitpid)

#### - **0 (Default):** The parent "blocks" (sleeps) until the child dies.

its like wait use block ,it doesn't do anything while waiting child to dies 

The options argument changes the behavior of the function. The most important one is **WNOHANG**.

#### WNOHANG (Wait No Hang)

Normally, wait() is a **blocking** call. This means the Parent "goes to sleep" and stops everything until a child dies.

**WNOHANG turns waitpid into a "non-blocking" call.**  
Instead of sleeping, the Parent just "checks in" on the child. It's like checking your email:

- **If the child is dead:** waitpid returns the PID of the child and reaps it.
    
- **If the child is still running:** waitpid does **NOT** sleep. It returns **0 immediately** and lets the Parent keep running its own code.
    

**Why is this useful?**  
It allows the Parent to do other work (like updating a loading bar or checking for user input) while occasionally checking: "Hey, is Child C done yet?"

#### WUNTRACED and WCONTINUED

These are for advanced process control:

- **WUNTRACED**: Tells the parent if a child was **stopped** (for example, if the user pressed Ctrl+Z in the terminal).
    
- **WCONTINUED**: Tells the parent if a stopped child has **resumed** running.
    

---

### 3. The "Wait Set"

The slide mentions a **"Wait Set."**

A Wait Set is simply a "Watch List" maintained by the OS. When you use waitpid with certain options, you are telling the OS: "Put these specific children on my watch list. Let me know when any of them change state."

### Slide 39: Putting a process to sleep

This slide explains how a process voluntarily gives up the CPU. In a multitasking system, it is inefficient for a process to "busy-wait" (running a loop that does nothing while waiting for something to happen) because it wastes CPU cycles. Instead, the process asks the OS to put it in a "Sleeping" state.

#### 1. The sleep() function

unsigned int sleep(unsigned int secs);

- **How it works:** When a process calls sleep, the OS removes the process from the "Ready Queue" (the list of processes waiting for the CPU) and puts it into a "Waiting Queue."
    
- **The Timer:** The OS sets a timer. When the timer expires, the OS moves the process back into the "Ready Queue" so it can resume execution.
    
- **Interruption:** If a signal (like a Ctrl-C or a hardware interrupt) wakes the process up before the time is up, sleep() returns the number of seconds that were remaining.
    

#### 2. The pause() function

int pause(void);

- **How it works:** Unlike sleep, pause() does not use a timer. It tells the OS: "Put me to sleep indefinitely. Do not wake me up until something happens."
    
- **The Trigger:** The process will stay asleep until it receives a **signal** (an asynchronous event).
    
- **Use Case:** This is commonly used in "Daemon" processes (background services) that spend 99% of their time doing nothing, waiting for a specific signal to wake them up and perform a task.


##  page 40 execve() :

### Slide 40: The "Brain Swap" (execve)

Until now, you have used fork(), which **clones** a process. But what if you want to run a totally different program (like opening Chrome or running ls)? You use execve.

#### 1. The Technical Process (The Overwrite)

When a process calls execve, it isn't starting a new process. Instead, it is **replacing itself**. The OS does a "Brain Swap":

1. **Wipe:** The OS wipes the current process's **Code** (text), **Data** (globals), and **Stack** (local variables).
    
2. **Load:** The OS loads a new binary file (the one you specified in filename) into that same memory space.
    
3. **Reset:** The CPU's Program Counter (PC) is reset to the start of the new program's main() function.
    

#### 2. What survives the swap?

Some things are NOT wiped. These are the "Identity" markers:

- **The PID:** The process keeps its original Process ID.
    
- **Open Files:** If the process had a file open, it stays open. (This is how Linux handles "output redirection").
    

#### 3. The "Point of No Return"

Because the original code is deleted from RAM, **execve never returns** if it works. If you write a line of code after execve, it will **never** be executed because the code that was supposed to run it has been erased and replaced by the new program.

---

### Slide 41: The "Fork-Exec" Pattern (The Industry Standard)

If execve replaces the process, why do we almost always see fork() and execve() used together?

**The Problem:** If the Shell (your terminal) called execve("ls") directly, the Shell would be replaced by ls. Once ls finished, the Shell would be gone, and your terminal would close!

**The Solution: The Fork-Exec Pattern**

1. **fork()**: The Shell clones itself. Now we have a Parent (Shell) and a Child (Clone).
    
2. **execve()**: The **Child** calls execve to replace its code with ls.
    
3. **wait()**: The Parent (Shell) stays alive and waits for the Child to finish. Once the Child dies, the Parent continues and gives you a new command prompt.
    

#### Understanding argv and envp (The Arrays)

execve requires two arrays of pointers:

- **argv (Argument Vector):** A list of strings. argv[0] is always the program name. The list **must** end with a NULL pointer so the OS knows where to stop reading.
    
- **envp (Environment Pointer):** A list of "KEY=VALUE" strings (e.g., USER=student). This also **must** end with NULL.
    

---

### Slide 42: Environment Variables (getenv, setenv)

Environment variables are like "global settings" for a process. They are stored as a list of strings in the envp array.

1. **getenv("NAME")**: Searches the list for a string starting with "NAME=". If it finds USER=john, it returns a pointer to the value "john".
    
2. **setenv("NAME", "VALUE", overwrite)**: Adds a new setting or changes an existing one.
    
3. **unsetenv("NAME")**: Deletes a setting.

### What you will see and why:

1. **The getenv part:** It prints your Linux username.
    
2. **The fork part:** It creates a child.
    
3. **The execve part:** The child suddenly transforms into the ls program. You will see a list of your files printed to the screen.
    
4. **The wait part:** The parent stays alive and prints the final message **after** the file list is done.
    

**Crucial Observation:** Notice that the printf("This will only print if execve FAILS!") never appears. This proves the "Point of No Return" from Slide 40.

### 1. setenv("MY_VAR", "Hello_Systems_Programming", 1);

#### "Where does the change happen?"

The change happens in a special area of the process's memory called the **Environment Block**.

Every process has a dedicated region of memory that stores "Key=Value" pairs (like USER=student or PATH=/bin). When you call setenv, the OS finds the environment block for your process and:

1. Checks if MY_VAR already exists in that list.
    
2. If it doesn't, it adds a new string "MY_VAR=Hello_Systems_Programming" to the end of the list.
    
3. If it does, it updates the value.
    

#### "Why use 1 and what is the difference?"

The 1 is the overwrite flag. It is a boolean (True/False).

- **If you use 1 (True):** It means "If MY_VAR already exists, **replace** the old value with the new one."
    
- **If you use 0 (False):** It means "If MY_VAR already exists, **do nothing**. Keep the old value."
    

**Example:**  
If the environment already had MY_VAR=OldValue:

- setenv("MY_VAR", "NewValue", 1)  →   Result: MY_VAR=NewValue
    
- setenv("MY_VAR", "NewValue", 0)  →    Result: MY_VAR=OldValue

### 2. char *args[] = {"/bin/ls", "-l", NULL};

#### "What is happening here?"

You are creating an **array of strings**. But in C, a "string" is actually just a char * (a pointer to the first character of the text). So, char *args[] is an **array of pointers**.

**Why these three specific items?**

1. **"/bin/ls"**: By convention, the first argument (args[0]) must be the **name or path of the program** you are running. The ls program expects its own name as the first argument.
    
2. **"-l"**: This is a flag. It tells the ls program: "Don't just list the files; show me the long format (size, date, permissions)."
    
3. **NULL**: This is the most important part. **The execve function has no way of knowing how many arguments you provided.** It doesn't know if you sent 2 arguments or 200. It keeps reading the array until it hits a NULL pointer. The NULL acts as a **Stop Sign**. If you forget the NULL, execve will keep reading random memory until the program crashes.

extern tells the compiler: "The variable environ is not defined inside this file. It is defined somewhere else (in the C Standard Library). Just trust me that it exists and let me use it."

#### "Why two pointers (**)?"

To understand char **, you have to build it from the bottom up:

3. **char ****: A pointer to a pointer. This is how we represent a **List of Strings**.

### 1. The First Argument: args[0] (The Target)

**What it is:** A pointer to a string containing the **full path** to the executable file.

- **Example:** "/bin/ls" or "/usr/bin/python3".
    
- **What the OS does:** The kernel looks at this path on the hard drive. It checks if the file exists and if you have permission to execute it. If the file isn't found, execve fails and returns an error.

**What it is:** An array of strings (a char **) called the **Argument Vector**.

- **The Content:** These are the flags or parameters you want to pass to the new program.
    
- **The Format:**
    
    - args[0] is the name of the program (by convention, this must match the first argument).

### 3. The Third Argument: environ (The Settings)

**What it is:** An array of strings containing the **Environment Variables**.

- **The Content:** These are "Key=Value" pairs that define the environment the program runs in.
    
- **Example:** {"USER=student", "PATH=/usr/bin", "HOME=/home/student", NULL}.
    
- **What the OS does:** The kernel copies this list into the new process's memory space. When the new program starts, it can call getenv() to find out who the user is or where the home directory is.
    

---

### 🛠️ What happens inside the CPU the moment this line is executed?

This is the "magic" part of Slide 40. The kernel performs a **total overwrite** of the process:

1. **The Wipe:** The kernel looks at the current process (the one that called execve) and **erases** its memory. The current code, the current variables, and the current stack are all deleted.
    
2. **The Load:** The kernel reads the binary file at args[0] from the disk and loads its machine code into the now-empty memory space.
    
3. **The Setup:** The kernel takes the args and environ arrays and places them at the top of the new program's stack so the new program can access them.
    
4. **The Jump:** The kernel resets the **Program Counter (PC)** to the first instruction of the new program's main() function.
    

### ⚠️ The "Point of No Return"

Because the kernel **deleted** the original code to make room for the new program, there is no way to go back.

If the execve call is successful, **the line of code immediately following it will never be executed.** The original program no longer exists in RAM; it has been completely replaced by the new one.

**If you see a return value from execve, it means the "Brain Swap" failed** (e.g., the file was not found), and the original program is still alive and continuing to run.

    - **SIGALRM (14):** Timer signal. Default: **Terminate**.
        
    - **SIGCHLD (17):** Child stopped or terminated. Default: **Ignore**.

    - The kernel delivers a signal by updating state in the destination process's context.

        .

### 3. Process Groups and Keyboard Signals

- **Process Group ID (PGID):**

- **Internal Events:**

### 5. Advanced Signal Concepts

- **Pending and Blocking:**
    
    - **Pending:** A signal is pending if it is sent but not yet received.
        
    - **Non-Queuing:** Signals are **NOT queued**. If a signal of type
        
        ```
        kk
        ```
        
        is already pending, subsequent signals of the same type
        
        ```

        ```

    - **Blocking:** A process can block the receipt of certain signals. Blocked signals are delivered but not received until they are unblocked.

- **Purpose:** Used to return immediately from deeply nested loops or functions to an outer layer (error recovery).
